# dsh-cot-flow — 设计文档

> 面向「展开的长思维链在流式输出时刻越久越卡」这一具体故障，
> 给出从成本模型、理论依据到实现取舍的完整推导。

版本 0.1.0 ｜ 适用于 DeepSeek Harness `>=0.1.7-0 <0.3.0-0`

---

## 1. 问题

DSH 在接受一次 LLM 响应时，思考文本（reasoning）以 token 流的形式逐块到达。
官方的思考体组件把**完整文本**交给 `MarkdownText`：

```
conversation.chat.reasoning.content → MarkdownText({ text, streaming: running, variant: "compact" })
```

`text` 每来一个 delta 就变一次，于是每一个 delta 都会触发一次**对整段思考的重新解析**。
症状与用户描述吻合：短思考无感，思考越长、在会话里越靠前，卡顿越明显——而且不是
"某一次很卡"，是"越流越卡"。

### 1.1 成本模型

设思考文本最终长度 $N$ 字符，流式共到达 $D$ 个 delta，第 $k$ 个 delta 时文本长度
$n_k = kN/D$（平均简化）。

官方路径单帧成本 ≈ $c_{\text{parse}}\,n_k + c_{\text{react}}\,V(n_k)$，
其中 $V$ 是由解析结果生成的虚拟节点数（大致正比于 $n_k$）。

$D$ 帧累计：

$$
T_{\text{official}} \;=\; \sum_{k=1}^{D} O(n_k) \;=\; O\!\left(\frac{ND}{2}\right) \;=\; O(N^2/\Delta)
$$

$\Delta = N/D$ 是平均 delta 长度，近乎常数。所以总成本对文本长度是**平方级**的，
而且这个平方项同时压在 JS 主线程上——它表现成丢帧，而不是"慢"，所以用户感知为"卡顿"。

反过来看，主线程每帧的时间预算只有约 16.7 ms，实际留给解析的可能只有几毫秒。
$N$ 到几千字符、$D$ 到几百帧时，单帧解析成本就会逼近预算，这正是"上下文长了以后"的临界点。

---

## 2. 目标与非目标

**目标**

- G1 把每帧成本从 $O(n_k)$ 降到 $O(\delta + |\text{tail}|)$，即**与总长度无关**。
- G2 最终渲染结果与官方一致：思考内容一个字符都不许丢、不许被改写。
- G3 失败可降级：任何一步出问题都退回官方渲染，绝不白屏。

**非目标**

- N1 不是"更好的思考排版"插件。视觉上的呼吸感只是切分带来的副作用，不是设计目标。
- N2 不改 host 侧、不改协议、不接管数据流。只替换一个渲染组件。
- N3 不试图解决推理服务本身的吞吐问题（那是上游的事）。

## 3. 理论基础

### 3.1 块级结构的空行可分性

CommonMark 的块级结构（block structure）由空行（blank line）分隔：段落、代码块、
标题、列表项、引用块之间以空行断开。这不是实现细节，而是规范层面的结构定义。

由此得到本设计的核心观察：

> **一个块一旦被空行终止，它的源文本就再也不会变了。**

因为流式只追加（append-only），而被空行终止的块是文本的**已完结前缀**；后续 delta 只
往后面追加，不可能回头修改这个前缀。The text of a committed block is immutable.

这就是整个方案的全部理论支点。它把"每帧重新解析全文"变成"每帧只解析尚未定稿的尾巴"。

### 3.2 前缀单调性（prefix monotonicity）

形式化一点。设时刻 $k$ 的文本为 $T_k$，且 $T_k \sqsubseteq T_{k+1}$（$T_k$ 是 $T_{k+1}$ 的前缀）。

定义切分函数 $\mathrm{seg}(T) = (s_1, \dots, s_m ; t)$，其中 $s_i$ 为已定稿段、$t$ 为未定稿尾巴。

**命题（稳定性）**：若 $T_k \sqsubseteq T_{k+1}$，则 $\mathrm{seg}(T_k)$ 的已定稿段序列是
$\mathrm{seg}(T_{k+1})$ 已定稿段序列的前缀。

理由：切分点只出现在"空行"之后，而空行的判定只依赖它之前的字符；追加不改变任何
已通过的切分点。∎

**推论**：$\mathrm{seg}$ 在追加序列上是**单调**的，因此可以对状态做增量复用，
且不需要返回任何"回溯"信息。

这条推论直接支撑了 §4.2 的扫描器（scanner）设计：只需保存 `pos`（已消费位置），
每次从 `pos` 往后扫新增字符。

### 3.3 增量解析的经典结论

增量解析（incremental parsing）的经典处理是 Wagner 与 Graham 的 rep-parse
（*Efficient and Flexible Incremental Parsing*, TOPLAS 1998；及更早的增量词法分析工作）：
解析器保留可复用的部分解析结果，只对发生变化的输入区间重新解析，其复杂度与
**编辑量**而非**文档总长**相关。

本设计做的是同一件事的粗粒度版本——不是 token 级的 rep-parse，而是**块级的结构复用**：
以段为单位缓存"已解析的渲染子树"，只对变化的尾块重新解析。

粗粒度换来的好处是：不需要实现 Markdown 的增量语法分析，也不依赖任何解析器内部 API，
因此可以做成一个纯渲染层的替换，对官方组件零侵入。

### 3.4 记忆化与结构共享

React 的 `memo` 提供浅比较层，等价于在组件边界上做一次"结构共享"（structural sharing）：
只要 props 的浅比较相等，整棵子树（包括其下的 Markdown 解析结果）被原样复用。

本设计依赖一个**引用稳定性假设**：

> 在一个 slot 的生命周期内，框架交给组件的 Factory 渲染函数（`renderFactorySlot`）是稳定的。

这是框架的既有契约（Factory 模块在 slot 生命周期内不重建）。因此段组件在比较时
**故意忽略** `render`：

```js
}, (a, b) => a.text === b.text && a.streaming === b.streaming); // lib/client.js:216-224
```

若把 `render` 纳入比较，一旦宿主在重渲染时递来新的闭包（`useCallback` 未命中、或
高阶组件包裹），memo 就整体失效，插件退化为官方行为——而且很难发现。
把不变量写进比较器，反而更稳。

### 3.5 摊还分析

设第 $k$ 帧新增 $\delta_k$ 字符，尾巴长度 $t_k$。

- 扫描：只读 $[\text{pos}_k, n_k)$，成本 $O(\delta_k)$。
- 渲染：已定稿段 O(1) 次字符串恒等比较；尾巴重新解析，成本 $O(t_k)$。

$$
T_{\text{flow}} \;=\; \sum_k O(\delta_k + t_k) \;=\; O(N) + \sum_k O(t_k)
$$

只要 $t_k$ 有界（尾巴不无限增长），第二项是 $O(D \cdot \bar t)$，与 $N$ 无关。
相比之下官方是 $O(N^2/\Delta)$。**这是一个从平方到线性的降阶**，而不是常数优化。

$t_k$ 无界的情形（超长单段落、未闭合围栏）见 §7。

## 4. 设计

### 4.1 切分规则

```
段 = 被「围栏外的空行」隔开的连续非空行
```

具体（`lib/client.js:125-156` `handleLine`）：

| 输入行 | 处理 |
|---|---|
| 处于围栏内 | 收进当前段；若本行是闭合围栏（同字符、长度不短于开启行、且无 info string）则闭合 |
| 是围栏起始行（`` ``` `` / `~~~`，≤3 空格缩进） | 收进当前段并进入围栏 |
| 全空白 | 定稿当前段（flush） |
| 是孤立分隔线（`---`/`***`/`___`） | 丢弃（它是思考里的噪声，且跨段后无意义） |
| 其它 | 收进当前段 |

围栏行正则：`/^\s{0,3}(`{3,}|~{3,})(.*)$/`（`lib/client.js:31`），解析成 `{ char, len, rest }`
（`fenceOf`，`lib/client.js:40-45`）。开启只看是否匹配；闭合按 CommonMark 收紧为
**同字符 + 长度不短于开启行 + `rest` 为空**。少了后两条，正在流式输出的代码块里只要
出现一行手打的 ` ```js `，块就被提前关掉，后面每个空行都开始切段——这是实测踩到过的坑。

空行**不保留**在段内，段间距离改由 CSS `gap: .62em` 表达（`lib/client.js:262-267`）。
这样段文本是"紧凑的"，缓存键更稳定，也顺手把思考里多余的连续空行折掉了。

### 4.2 扫描器状态机

状态（`createState`，`lib/client.js:85-99`）：

```js
{ text, pos, head, tailAnchor, inFence, fenceChar, fenceLen, para, segs, tail }
```

分别是：上次的全文快照、已消费到的字符位置、快照首尾各 24 字符的锚点、是否在围栏内、
当前围栏的字符与长度、当前段的累积行、已定稿段、待定稿尾巴。

`scan(st, text)`（`lib/client.js:158-189`）：

1. **续写判定**：`continues(st, text)`（`lib/client.js:109-116`）比较长度与首尾锚点，
   常量代价；不成立则整体重建（文本被替换、被 rewind、或换了会话）。
   早先版本比的是整个已消费前缀——`startsWith(st.text.slice(0, pos))` 每帧都要分配并比对
   $O(n)$ 个字符，恰好把要消灭的复杂度又加了回来；锚点法把它压回 $O(1)$，代价见 §7.5。
2. 从 `pos` 开始逐行取到最后一个 `\n`，逐行喂给 `handleLine`。
3. 剩余不完整的一行与当前段拼成 `tail`。

关键点：**只消费到最后一个换行**。不完整的行永远留在 `tail` 里，
所以每个字符最多被处理两次（一次作为尾行，一次作为完整行）。这是 $O(N)$ 而非
$O(N \cdot D)$ 的直接原因。

### 4.3 渲染分解

`CotFlowBody`（`lib/client.js:226-260`）输出

```
<div data-cot-flow>          ← flex 列，gap 承担段间距
  <div data-cot-flow-seg>text: s0, streaming: false  ← 定稿段，永久命中 memo
  ...
  <div data-cot-flow-seg>text: tail, streaming: running ← 尾段，每帧重解析
</div>
```

每个段落通过 `renderFactorySlot("conversation.chat.reasoning.content", { text, running })`
渲染——即**复用官方注册的 Factory**，而不是自己再实现一遍 Markdown 渲染。
这样样式、语法高亮、代码块行为全部与官方一致，插件只负责"切"和"缓存"。

### 4.4 生命周期与降级

`apply(ctx)`（`lib/client.js:279-307`）做两件事，都用 `ctx.effect` 管理：

1. 注入一份 `<style>`，卸载时移除。
2. `ctx.slots.inject("conversation.chat.reasoning.body", () => ctx.slots.register({name, priority: 50}, CotFlowBody))`。

注册优先级 **50 < 官方的 100**：按框架「替换项使用更小数值」的约定，本组件覆盖官方思考体。

所有失败路径都 `try/catch` 后返回 noop disposer，并记一条 error 日志，**不抛出**。
最坏情况是插件静默不生效、官方渲染照常——满足 G3。

### 4.5 幂等性

`scan` 对同一 `text` 重复调用是幂等的（前缀检查成立时不再消费任何新字符）。
这一点顺带让插件在 React 严格模式的双调用、以及并发渲染的回放中保持安全。

## 5. 正确性

三条不变式，全部有测试覆盖（`test/scan.test.mjs`，16 项断言）：

- **I1 内容守恒**：切分前后的非空行序列完全相同（段内换行保留、围栏内空行不切、围栏内分隔线保留）。
- **I2 增量等价**：逐字符喂入的最终状态，与一次性扫描的结果逐段相同。
- **I3 回退确定**：文本被改写/变短时，重建结果与对新文本首次扫描相同。

另有边界用例：单段落不切、空行切段、连续空行折叠、前导空行丢弃、未闭合围栏整体留在尾段、
孤立分隔线删除、`~~~` 围栏。

## 6. 可观测性

`window.__dshCotFlow` 暴露计数：`{ renders, scans, scanMs, lastScanMs, segs, chars }`。

排查时看三个数就够：

- `scans` 应约等于 delta 数（每帧一次）；
- `lastScanMs` 应稳定在亚毫秒级，且**不随 `chars` 增长而增长**——这是本设计是否真的生效的判据；
- `segs` 是当前段数，若始终为 0 或 1，说明文本里没有空行，切分无从下手（见 §7.2）。

DOM 上还有 `[data-cot-flow]` 与 `[data-cot-flow-segments="N"]`，可直接在元素检查器里确认是否接管。

### 6.1 持久探针

内存计数随窗口消失，于是"这个组件到底渲染过没有"在事后无法回答——插件接管了 slot 和从未运行过，从外部看毫无差别。为此最初若干次渲染会把计数镜像进 `localStorage["dsh-cot-flow:probe"]`，写满 4 次后静默（避免写放大）。

这条探针是唯一能从渲染进程之外验证接管的证据。应用运行中直接搜 leveldb 即可：

    AppData\Roaming\@deepseek-ai\dsh-desktop\Local Storage\leveldb\*.log   → 搜 dsh-cot-flow:probe

首次实测（2026-10-27 17:45，HMR 推送新代码后写入）：

    {"at":"2026-10-27T09:45:52.573Z","renders":394,"scans":387,"segs":3,"chars":333,"lastScanMs":0,"scanMs":3.7}

读法：387 次扫描累计 3.7ms，均值 0.0096ms；333 字符的思考被切成 3 段；`renders` 比 `scans` 多 7 次，差额正是 `useMemo` 在文本未变时省掉的重扫。这与 §3.5 的摊还预测一致：单次增量代价与文本总长基本脱钩。

## 7. 已知边界

诚实列出。这些都是"切分粒度 = 空行"这一决定带来的固有代价。

### 7.1 可含空行的块

CommonMark 里存在**内部允许空行**的块：

- **缩进代码块**（4 空格缩进）可以包含空行；
- **HTML 块** 的若干类型以空行作为结束条件，类型 1–5 的空行处理更复杂；
- **引用块** 与**松散列表项**内部允许空行。

遇到这些结构，本插件会把它切成两段。渲染结果是"内容不丢、但结构被拆成相邻两段"。
对思考文本而言几乎不可见（思考里很少出现缩进代码块或 HTML 块），但这是与官方渲染
**不严格等价**的地方，需要明确记录。

$$...$$ 块级数学式同理（多数渲染器把它当段落级，跨空行会断开）。

### 7.2 无空行的超长单段

若整段思考没有空行（或只有一个巨大段落），$t_k \to n_k$，尾巴成本退化回 $O(n_k)$，
插件等价于官方实现。此时不会更坏，但也不会更好。

这是设计上的**软失效**（graceful degradation），不是 bug。真实思考文本几乎总是分段落的，
所以实践中很少触发。

### 7.3 未闭合围栏

围栏开启后直到文本结束都没闭合，则整段内容留在尾巴里，同样退化为官方的行为。
一个正在流式输出中的超长代码块属于这种情况——此时确实会卡，但那是唯一正确的渲染方式
（代码块内容不完整时提前定稿反而会闪烁重排）。

闭合判定按 §4.1 收紧之后，流式中的代码块不会被内部「看起来像围栏」的行提前结束：
` ```js ` 带 info string、`~~~` 不认反引号、```` ```` ```` 不会被三个反引号关掉。

### 7.4 分隔线丢弃的信息损失

孤立分隔线（`---`/`***`/`___`）被删除。这是**有意的**：在 chat 的紧凑思考视图里，
横线是纯噪声，且跨段之后会与段间距叠加成奇怪的留白。
若上游用它做视觉分章，语义会丢失——目前观察不到这种用法。

---

### 7.5 锚点比较漏掉中心改写

`continues` 只比较长度与首尾 24 字符，于是「长度不变、首尾相同、只有中段被换掉」的替换
会被当成续写，已定稿段继续显示旧文本。真实数据里不会发生：思考文本由流式增量单调累积，
重试会换消息、也就是换组件实例，从而触发一次完整重建。全量前缀校验能消灭这个缺口，
代价是每帧 $O(n)$——与插件存在的理由直接冲突，故不采用。

## 8. 备选方案与取舍

| 方案 | 结论 | 理由 |
|---|---|---|
| 节流（throttle/deprioritize）delta 刷新 | 否 | 只是把平方曲线的斜率改小，$N$ 大时仍爆炸；且牺牲流式手感 |
| 改用更快的 Markdown 解析器 | 否 | 需要替换官方 Factory，样式/语法高亮全部要重做，且仍逐帧全量解析 |
| 虚拟化整条消息列表 | 否 | 解决的是另一问题（消息条数多），对单条长思考无效；改动面巨大 |
| token 级增量解析（rep-parse） | 否 | 需要解析器内部结构，无法在纯渲染层实现；收益只比块级多一点 |
| **块级切分 + memo** | **是** | 纯渲染层、零侵入、平方→线性、失败可降级 |

选块级的核心理由是**侵入面最小**：它不碰解析器、不碰协议、不碰官方 Factory，
只换一个组件，并且天然可回滚。

4. **向上游提议**：这个优化在官方组件里也成立（对任何"流式 + 全量解析"的 Markdown 视图都成立），
   作为插件只是绕开改动风险。
